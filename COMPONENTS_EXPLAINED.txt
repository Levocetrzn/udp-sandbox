1. SYSTEM ARCHITECTURE & DESIGN PHILOSOPHY
================================================================================
UDP-Scope is designed from the ground up as a zero-dependency, self-contained
educational and engineering platform for understanding Layer 4 User Datagram
Protocol (UDP) transport mechanics.

Key Engineering Tenets:
- 100% In-Browser Execution:
  All packet physics, network delays, loss models, checksum arithmetic, and
  packet disassembling run entirely in the browser using client-side JavaScript
  and HTML5 Canvas 2D. No server-side daemon or socket proxy is required.
- Strict RFC Conformance:
  - UDP Header fields conform exactly to RFC 768 (8 bytes: Source Port,
    Destination Port, Length, Checksum).
  - Checksum calculation strictly implements RFC 1071 (16-bit one's complement
    addition with end-around carry across pseudo-header, header, and payload).
  - IPv4 encapsulation references RFC 791 (20-byte base header, protocol 17).
- Reactive Particle-Based Simulation:
  Canvas animations use requestAnimationFrame() loops with delta timing,
  particle emitter physics for packet drops, laser pulse trajectories for links,
  and stateful packet objects that react dynamically to user impairment sliders.

4. MODULE 2: UDP VS TCP COMPARATIVE SIMULATION (TAB 2)
================================================================================
File Location: index.html (Lines 338-493), src/app.js (Lines 685-980)

This module provides a live, synchronized side-by-side benchmark contrasting
UDP's connectionless best-effort delivery against TCP's connection-oriented,
guaranteed-delivery sliding window.

4.1. Dual-Lane Synchronized Canvases (#udp-lane-canvas, #tcp-lane-canvas)
- Lane 1 (UDP - User Datagram Protocol):
  - Canvas: #udp-lane-canvas.
  - Mode: Fire-and-Forget.
  - Behavior: Packets stream continuously from left (Client) to right (Server).
    Packets subjected to loss drop instantly and disappear. The sender does NOT
    track them, receives NO acknowledgments, and never attempts retransmission.
- Lane 2 (TCP - Transmission Control Protocol):
  - Canvas: #tcp-lane-canvas.
  - Mode: Sliding Window with ARQ (Automatic Repeat reQuest).
  - Behavior:
    1. Initial 3-way handshake simulation (SYN -> SYN-ACK -> ACK).
    2. Data segments stream with sequence numbers.
    3. As segments reach the server, small cyan ACK packets flow in reverse
       (right-to-left) back to the sender.
    4. If a data segment is dropped (red flash), the sender notices the missing
       ACK, triggers a timeout timer, and automatically retransmits the lost packet.

4.2. Experiment Controls & Sliders (.cmp-controls-card)
- "Start Experiment" (#btn-compare-start) / "Stop" (#btn-compare-stop): Launches
  or halts the concurrent simulation race.
- Simulated Loss Rate (#cmp-loss, #cmp-loss-val): Configurable from 0% to 80%
  to demonstrate how packet loss impacts throughput and latency on both protocols.
- Simulation Speed (#cmp-speed, #cmp-speed-val): Slow-motion (0.5x) to high-speed (3x).

4.3. Live Telemetry Counters (.cmp-live-stats)
- UDP Card (#cmp-stat-card.udp-card):
  - Datagrams Sent (#cmp-udp-sent)
  - Delivered (#cmp-udp-recv)
  - Lost (#cmp-udp-lost)
  - Retransmissions (#cmp-udp-retry): Stays at 0 (illustrating no retransmissions).
- TCP Card (#cmp-stat-card.tcp-card):
  - Packets Sent (#cmp-tcp-sent)
  - Delivered (#cmp-tcp-recv)
  - Lost (Triggered Retransmit) (#cmp-tcp-lost)
  - ACKs Returned (#cmp-tcp-acks)

4.4. Protocol Specification Matrix (.cmp-table)
- A 10-point side-by-side comparison matrix covering: Connection State,
  Header Overhead (8B vs 20-60B), Delivery Reliability, Packet Ordering,
  Flow Control, and Primary Use Cases.

6. MODULE 4: RFC 768 / RFC 1071 CHECKSUM ENGINE (TAB 4)
================================================================================
File Location: index.html (Lines 943-1049), src/app.js (Lines 1755-2450)

This module provides an interactive visual and mathematical simulator of the
Internet Checksum algorithm defined in RFC 768 and RFC 1071.

6.1. The 12-Byte IPv4 Pseudo-Header
RFC 768 specifies that UDP checksums must cover a 12-byte "pseudo-header" to ensure
that misrouted datagrams (e.g. corrupted IP addresses) are rejected:
- Source IPv4 Address (4 bytes / two 16-bit words)
- Destination IPv4 Address (4 bytes / two 16-bit words)
- Zero Padding (1 byte: 0x00) + Protocol Number (1 byte: 17 / 0x11) = 1 word
- UDP Length (2 bytes / one 16-bit word)

6.2. 16-Bit One's Complement Addition Engine
The engine computes:
  Sum = Pseudo-Header Words + UDP Header Words + Payload Words
- Words are 16 bits wide (big-endian).
- If the payload has an odd number of bytes, a 0x00 pad byte is appended.
- End-Around Carry: If addition exceeds 16 bits (sum > 0xFFFF), the overflow
  bits (sum >> 16) are wrapped and added back to the lowest 16 bits:
    sum = (sum & 0xFFFF) + (sum >> 16)
- Checksum Inversion: The final checksum is the bitwise NOT (~sum & 0xFFFF).
  If the result is 0x0000, RFC 768 mandates transmitting it as 0xFFFF (since 0x0000
  signifies "checksum omitted").

6.3. Checksum Animation Canvas (#cs-canvas)
- An animated Canvas 2D visualization rendering a vertical stack of 16-bit words.
- Words are color-coded:
  - Cyan: IPv4 Pseudo-Header words
  - Purple: UDP Header words
  - Green: Payload data words
  - Gold: Running accumulated 16-bit sum
- A pulsing carry indicator animates end-around carry additions in real time.

6.4. Step-by-Step Math Breakdown (#cs-steps-list)
- Detailed textual ledger showing every intermediate addition:
  Step N: 0xXXXX + 0xYYYY = 0xZZZZ [Carry: +1 -> 0xAAAA]

6.5. 16-Bit Binary Register View (#cs-bit-table)
- Visualizes 16 distinct bit columns (Bit 15 down to Bit 0) for each word,
  allowing students to visually inspect bit transitions and carries.

6.6. Receiver Verification Proof (#cs-verify-section, #cs-verify-canvas)
- The Receiver sums ALL incoming words PLUS the received checksum.
- Mathematical Proof:
  Since Checksum = ~Sum,
  Receiver Sum = Sum + Checksum = Sum + (~Sum) = 0xFFFF (All 1s in binary).
- In 1's complement arithmetic, 0xFFFF represents negative zero. Inverting 0xFFFF
  yields 0x0000, mathematically proving 100% datagram integrity!

6.7. Corruption & Bit-Flip Demonstration (#cs-btn-corrupt)
- Inverts a single random bit in the payload without recalculating the checksum.
- When verified, the receiver sum does NOT equal 0xFFFF. The engine flags an
  immediate CHECKSUM MISMATCH / INTEGRITY ERROR, illustrating how UDP detects
  damaged data.
